<objective>
Prove that a resumed session comes back as it left — model, reasoning effort, plan state — that a drafted plan
survives a quit, and state which of those settings comes from the session and which from config.

Purpose: SESS-01, SESS-03 and SESS-04 decide whether a session can be trusted across a restart. The restore
paths exist (`session_setup.rs`, `plan_mode.json`) but nothing proves them end to end, and the provenance
question — "why is the permission chip the same after resume?" — is exactly where a plausible-sounding wrong
answer would be written. This plan answers it from the code and pins each half with a test.

Output: one headless resume test, an extended plan-approval-resume scenario with a cast, one committed evidence
item, and one user-guide paragraph.

Execution shape: **build host**. Rust 1.94.0 pinned, >=150 GB free, shared `CARGO_TARGET_DIR`, and a release
binary built from the tree that includes 02-04's changes (copied to a private path for the pty run). No key and
no network: the mock provider is loopback.

Scope note: SESS-02 (plan mode read-only in every permission mode) is **not** here. It lives in 02-06 with
PERM-03/PERM-04, because it shares the mode-chip and plan-gate surface that 02-06 already loads, and keeping it
here pushed this plan to 1.4x the smart-zone budget. Nothing in SESS-02's requirement changes.
</objective>
