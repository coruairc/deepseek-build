# Phase 02 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** This is a **verification** phase over a Rust `ratatui` TUI. It adds no product surface. Exactly
three user-visible surfaces are in scope, and this contract binds only them:

1. **The interactive permission prompt** — the allow-once / allow-for-session / reject rows and the
   high-signal security warning (`crates/codegen/xai-grok-pager/src/views/permission_view.rs`, fed by
   `crates/codegen/xai-grok-workspace/src/permission/prompter.rs`).
2. **The permission-mode indicator** — the mode/permission chips on the prompt's info row, the status-bar
   `plan` chip, the plan-mode scrollback rows, and the mode toasts — as shown before quit and again after
   `--resume` (`views/prompt_widget/mod.rs::mode_flags`, `app/agent_view/plan.rs`, `app/agent_view/render.rs`,
   `scrollback/blocks/session_event.rs`).
3. **The headless denial text** — the two messages a `-p` run writes when a permission-gated tool cannot be
   approved (`crates/codegen/xai-grok-pager/src/headless.rs`). Copy and stream only; no layout.

Everything else in Phase 2 (the live session, the egress measurement, the leak scan, resume provenance) is
non-visual or is evidence capture of the surfaces above. The one product change this contract justifies is
the JSON-path headless denial string (PERM-02) — see §Copywriting Contract.

**Upstream decisions consumed:** `02-CONTEXT.md` §Permission surface and §Resume fidelity (locked),
`REQUIREMENTS.md` PERM-01/02/03/04 + SESS-01/02/03/04, `ROADMAP.md` Phase 2 criteria 4–5,
`01-UI-SPEC.md` for house shape and scoping discipline.

**Grounding rule.** No new colour, spacing, typography, glyph, or component token exists in this phase. Every
visual value below resolves to an existing `Theme` token (`crates/codegen/xai-grok-pager-render/src/theme/`,
default `DeepSeekMonokai`) or to the terminal cell grid. Where a value is a *literal* (a label, a separator,
a glyph), it is quoted so the evidence can be matched byte-for-byte.

## Spacing Scale

A terminal is measured in painted **columns and rows**, not pixels; the template's 4-px scale does not apply.
Every value below already exists in the render code and is restated so the evidence can assert it.

| Token | Value | Usage |
|-------|-------|-------|
| accent-gutter | 3 columns | prompt content starts at `area.x + 3`; the accent bar glyph owns column `area.x` |
| content-inset | 5 columns total | `content_width = area.width - 5` (3 left + 2 right) |
| shortcut-column | 2 columns | `"1 "` … `"9 "`; blank for index ≥ 9 (`SHORTCUT_LABELS[0] == "  "`) |
| marker-column | 4 columns | `"(●) "` on the cursor row, `"(○) "` otherwise |
| flag-separator | 3 columns | `" · "` (U+0020, U+00B7, U+0020) between model name and each chip |
| row-step | 1 row | every prompt row is exactly one row; there is no vertical padding inside the panel |
| collapsed-body-cap | 5 rows | `PERMISSION_COLLAPSED_ROWS`; the 6th row is replaced by the `... Ctrl-F to expand` indicator |
| panel-height-cap | `max(screen/2, 10)` rows, ≤ 80% of screen | `permission_view_height`; lifted to the full screen when `args_expanded` |
| bottom-pad | 1 row | `vpad_bottom` under the option list |

Exceptions: none. No padding, gutter, or separator changes in this phase. The panel is not re-laid out; only
its **contents** are asserted.

## Typography

There is one type size in a TUI: the terminal's cell. The contract is therefore glyph width, weight, and
tone — two weights, not four sizes.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Prompt title (`Allow \`cargo test\`?`) | 1 cell | **bold**, `fg(theme.text_primary)` | 1 terminal row |
| Option label (cursor row) | 1 cell | **bold**, `fg(theme.text_primary)` | 1 terminal row |
| Option label (other rows) | 1 cell | normal, `fg(theme.text_primary)` | 1 terminal row |
| Shortcut digit | 1 cell | normal, `fg(theme.accent_user)` | 1 terminal row |
| Info-line chip (mode / permission) | 1 cell | normal, flag colour blended toward the prompt bg at the existing `flag_opacity` | 1 terminal row |
| Hint text (`← → narrow scope`, `e edit pattern`, `... Ctrl-F to expand`) | 1 cell | normal, `fg(theme.text_secondary)` + `DIM` for the prose; the key glyphs and `... Ctrl-F to expand` use `fg(theme.gray)` with no `DIM` (`permission_view.rs:570-580, 1353-1361`) | 1 terminal row |
| Headless denial (stderr) | the terminal's own | the terminal's own | one physical line per message; no wrapping is added by the product |

- Every character the contract fixes is width-1 ASCII or one width-1 glyph: `⚠`, `·`, `●`, `○`, `←`, `→`,
  `❯`, `…`, `✓` (three toasts), `✗` (the two pattern-editor strings). Keep it that way — the column math in
  `build_permission_option_line` assumes it.
- No italic, underline, reverse, or blink is added by this phase. Reverse video appears only through the
  existing `theme.selection_overlay()` / `block_cursor_over()` paths on the terminal-native palette.
- The security warning is **not** bold and **not** larger. It is one row of ordinary cell text in the
  warning tone. Emphasis comes from tone and from being the first line, not from weight.

Hard rules:

- **The reject row is not red.** `No, reject (type to add feedback)` renders in `gray` / `text_primary` like

  failure state, and a colour change would be a new interaction contract the phase has not earned.
- **No new hex value, no new token, no new style helper.** No colour is added for the mode chips, the
  warning, or the headless text.
- The chips keep the existing blend path: `mode_flags` dims a flag toward the prompt bg at `flag_opacity`

  or add a second opacity.
- Headless stderr is plain terminal text. No ANSI colour, no OSC, no prefix stripping beyond the `Error: `
  that `main` already adds.

## Copywriting Contract

Copy is fixed here. Every quoted string is byte-exact, including the U+00B7 `·` separator and the single ASCII
space inside ` · `. The pty evidence matches these strings, so a reworded label is a defect.

### The three canonical outcomes (PERM-01)

The requirement names allow-once / allow-for-session / reject. Those are **row identities** on the wire
(`allow-once`, an `AllowAlways` row, a reject row), not a single fixed label: the allow-once label is
access-kind specific today, and the contract preserves that.

| Outcome | Wire id / kind | Rendered label — by access kind |
|---------|----------------|---------------------------------|
| allow-once | `allow-once` (`AllowOnce`) | shell: `Yes, proceed` · edit: `Yes` · MCP tool: `Yes` · web_fetch: `Yes, allow once` · agent message: `Yes, send once` · fallback client: `allow once` |
| allow-for-session (persistent allow) | `allow-always-command`, `allow-always-mcp`, `allow-always-domain`, `allow-edits-session` (`AllowAlways`) | shell: `Always allow: <primary command>` · MCP: `Always allow: <tool>` (server scope: `Always allow: all tools from <Server>`) · web_fetch: `Yes, always allow <domain> for this project` · edit: `Yes, allow all edits during this session` |
| reject | `reject-once` (`RejectOnce`) | always `No, reject (type to add feedback)` — the view replaces the wire label (`build_reject_once_line`) |
| reject-always (trailing row, not one of the three) | `reject-always-command`, `reject-always-mcp`, `reject-always-domain` | `Never allow: <primary command>` · `Never allow: <Display Tool>` · `No, never allow <domain> for this project` |
| always-approve escalation (first row) | `enable-always-approve` (`AllowOnce` kind) | `Yes, and don't ask again for anything (always-approve mode)` |

Accuracy rule for the middle row: the persistent allows are **project-scoped**, not session-scoped, except
`Yes, allow all edits during this session`, which is literally session-scoped. Do not reword `Always allow:`
or `Never allow:` to say "this session"; the web_fetch label's `for this project` is the honest phrasing and
is already correct. A label that overpromises narrower scope than the grant persists is a copy defect.

Row order for a shell prompt (top to bottom), which the cast must show in order:
`enable-always-approve` → `allow-always-command` (only when the row is effective) → `allow-once` →
`reject-once` → `reject-always-command`.

### Default cursor

`resolve_initial_cursor` puts the cursor on the **always-approve row by identity** when the user has neither
configured `[ui].default_selected_permission` nor confirmed a previous prompt; after the first confirmation
it sticks to the last-used kind (and a concrete sticky kind never escalates to the global row). This is
existing security-relevant behaviour, pinned by `permission_cursor.rs` tests. **This phase does not change
it** — the pty scenario must not assert or require a different initial row, and must not add
`--always-approve`-style convenience to the prompt.

### The high-signal security warning (PERM-01)

One fixed-text row, owned by the harness and never carrying command text, prepended above the question:

```
⚠ Security warning: <finding>; <finding>; …
```

- Prefix: `⚠ Security warning: ` (U+26A0, one space, capital S, colon, one space).
- Findings are joined by `; ` (semicolon + one space) in the enum's canonical order
  (`UnparseableShell`, `OpaqueShell`, `ExecOrAmbientGit`, `EnvInjection`, `DangerousCommand`,
  `SpecialExecSurface` — i.e. `ClassifierSecurityFinding` variant order, filtered to the six high-signal
  variants).
- Exact finding text (do not paraphrase):

| Variant | Rendered text |
|---------|---------------|
| `UnparseableShell` | `shell structure could not be fully parsed` |
| `OpaqueShell` | `invokes a nested or dynamically supplied shell command` |
| `ExecOrAmbientGit` | `may run code via an execution callback or ambient Git configuration` |
| `EnvInjection` | `sets environment variables that can change which code executes` |
| `DangerousCommand` | `a destructive or high-impact command` |
| `SpecialExecSurface` | `options or tools that can write arbitrary output, execute code, override config/identity, or disclose the process environment` |

- Worked strings: `rm -rf build` → `⚠ Security warning: a destructive or high-impact command`.
  `bash -c "$X"` → `⚠ Security warning: invokes a nested or dynamically supplied shell command`
  (`UnresolvedArgument` is low-signal and must stay filtered out).
- The warning renders **in every permission mode**, not only auto: the shell prepends it on the ordinary
  prompt path too, so a call that still reaches a prompt under `always-approve` (a `deny`/`ask` rule, a
  protected edit, a hook ask) carries the same warning. Do not gate it on `auto`.
- The warning row uses `theme.warning`, weight normal. The `⚠` glyph is the only non-ASCII in the row; the
  pty assertion matches on the substring `Security warning:` so a legacy-ConHost glyph fallback does not
  fail the evidence.
- Low-signal findings (`FileWrite`, `UnvettedEnv`, `UnresolvedArgument`, `FailClosedPolicy`) never produce a
  warning. Adding one is a copy defect, not a judgement call.

### The mode indicator (PERM-03)

Chips sit on the prompt's info row, right-aligned, after the model name, each preceded by ` · `:

```
deepseek-flash · plan · always-approve
deepseek-flash · plan · auto-review
deepseek-flash · ask
deepseek-flash · always-approve
```

| Chip text | Source | Colour |
|-----------|--------|--------|
| `plan` | `effective_plan` / `prompt_row_mode_label` | `accent_plan` |
| `plan approval` | plan-approval view open | `accent_plan` |
| `commenting` / `commenting L{n}` / `commenting L{a}-{b}` | plan commenting | `accent_plan` |
| `ask` | `SessionMode::Ask.as_id()` | `accent_success` |
| `always-approve` | `PermissionLabel::AlwaysApprove` | no override → muted gray |
| `auto-review` | `PermissionLabel::Auto` | `accent_system` |
| *(nothing)* | `PermissionLabel::Ask` | the ask permission state renders **no** chip |

Rules: the mode label and the permission label are independent axes — neither hides the other. `Default` and
`Plan` produce no session-mode chip by themselves (plan reaches the row through the plan label). The
permission id `always-approve` and the display text are the same token; `auto` is displayed as
`auto-review` (never `auto`), and `default` is never displayed.

Other indicator surfaces, same vocabulary:

| Surface | Copy |
|---------|------|
| Status-bar chip | `plan` (lowercase, `accent_plan`, after the background-task line) |
| Scrollback row, agent-entered plan mode | `Agent entered plan mode · active permission mode: {ask\|auto-review\|always-approve} · file edits outside session plan.md blocked until plan mode exits` |
| Scrollback row, plan review closed | `Plan approved · plan mode off · active permission mode: {…}` / `Plan abandoned · plan mode off · active permission mode: {…}` |
| Shift+Tab banner | `Switched to mode: Normal` / `Ask` / `Plan` / `Auto-review` / `Always-Approve` / `Agent` (`Normal` is the Default permission mode — `app/dispatch/modes.rs:752, 771, 788, 823`; the toast for the same state reads `✓ Permission mode: Default`) |
| Permission-mode commit toast | `✓ Permission mode: Default` · `✓ Permission mode: Ask` · `✓ Permission mode: Auto-review` |
| Always-approve on toast | `⚠ Always-approve ON: all tool actions auto-run` |
| Always-approve on **under plan mode** | `⚠ Always-approve ON: plan mode still blocks file edits until you exit plan mode` |

### The headless denial (PERM-02)

Two lines, both on **stderr**, on both the plain and the `--output-format json` invocation. Exit status is 1.

1. **Hint line** (unchanged; emitted by `permission_cancel_hint` before the turn error). One physical line:

```
Turn ended: a permission-gated tool was cancelled because headless mode cannot prompt for approval. Re-run with --always-approve, or choose a non-interactive permission mode such as --permission-mode auto.
```

2. **Final error line** (this is the phase's one product change). Today `main` renders the `anyhow!` payload
   as `Error: {msg}`, and `{msg}` names only one flag:

| | Copy |
|---|---|
| Current `{msg}` | `permission-gated tool cancelled; pass --always-approve to approve it` |
| **Required `{msg}`** | `permission-gated tool cancelled; re-run with --always-approve, or choose a non-interactive permission mode such as --permission-mode auto.` |
| **Required rendered line** | `Error: permission-gated tool cancelled; re-run with --always-approve, or choose a non-interactive permission mode such as --permission-mode auto.` |

Copy rules for both lines:

- Name `--always-approve` **and** the mode flag, in that order, exactly as spelled above.
- Never suggest `--permission-mode always-approve`: `--permission-mode` accepts only
  `default | acceptEdits | auto | dontAsk | bypassPermissions | plan`, so that suggestion would fail clap
  validation. `--always-approve` is a separate flag. This is the whole reason the current text is wrong.
- Name `--permission-mode auto`, not `--permission-mode=auto`.
- Do not name a config file, a slash command, or `--allow` in these lines; they are the headless,
  non-interactive path only.
- The stderr hint appears only when `--always-approve` was **not** passed (`permission_cancel_hint` returns
  `None` for `is_yolo`). That is the fail-closed path and must stay that way: a yolo run ends `Ok(())` with
  no denial line.
- Do **not** add a field to the JSON result object to carry the hint. `--output-format json` keeps
  `stopReason: "cancelled"` on stdout and the two stderr lines; a new schema key is a new product surface and
  is out of scope for this phase.

| Element | Copy |
|---------|------|
| Primary CTA | `1 (●) Yes, proceed` — the allow-once row, confirmed with `Enter` or `1` |
| Empty state (no pending prompt) | nothing renders: the panel is absent and the prompt row shows the info line only. No placeholder, no `no permission requests` |
| Error state (prompt failed / queue rotated) | the request is dropped and no panel remains; existing toast behaviour, unchanged. No new error string |

## UI Considerations

Applicable state considerations resolved: 6 covered, 0 backstop, 0 unresolved.

Element kinds: the permission prompt is `interactive-control` + `list-collection`; the mode indicator and the
headless denial are `static-content`. That raises `error`, `overflow`, `zero-one-many`, `long-text` (and
`empty` for the collection). `loading` / `media` / `partial` / `populated` do not intersect those kinds and
are dismissed for that reason, not silently.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | permission prompt (list-collection) | ✅ covered | No pending request renders no panel and no placeholder; the info row is unchanged. Specified in the Copywriting Contract `empty` row. |
| error | permission prompt (interactive-control) | ✅ covered | A failed or rotated request drops the panel with the existing toast behaviour; no new error string is introduced, so there is no unowned copy. |
| overflow | permission prompt option list; prompt body | ✅ covered | The option list scrolls via the existing `options_scroll_offset` inside `permission_view_height`'s cap; the shell/edit body collapses at 5 rows and the 6th row becomes `... Ctrl-F to expand`. Neither behaviour changes. |
| zero-one-many | permission prompt option list | ✅ covered | 1 row (non-TUI client), 2–3 rows (edit / MCP), 5 rows (shell) all render with the same prefix width; `shortcut_label` blanks the prefix past index 9 rather than widening the row. |
| long-text | option labels, prompt title, security warning | ✅ covered | The dynamic scope suffix on a persistent-allow row truncates to `row_width − prefix` via `truncate_str`; command bodies soft-wrap at the content width and stop at the collapsed cap. The warning is a single fixed-text sentence that carries no command text, so it cannot grow with the command. |
| long-text | headless denial | ✅ covered | Both lines are single fixed sentences with no interpolated path, host, or command; a terminal wraps them and the product adds no wrapping of its own. |

## Interaction Contract

### Permission prompt

| Behaviour | Contract |
|-----------|----------|
| Appearance | The panel mounts above the prompt when a `RequestPermissionRequest` arrives. It takes focus, the composer text is stashed and cleared, and the active pane switches to the prompt if the scrollback had it. |
| Row selection | `↑` / `↓` (or `k` / `j`) move the cursor row (`active_idx`); digits `1`–`9` select a row outright; `Enter` confirms the cursor row. The cursor row carries `theme.selection_overlay()` (band on RGB, reverse video on the terminal-native palette) and the label goes bold; other rows stay plain. |
| Pointer | A single click moves the cursor to the row under the pointer; a double click confirms it. Hover paints `theme.hover_overlay()`. Clicking outside the option rows hands the event to the followup input when it is focused. |
| Always-approve shortcut | `Ctrl-O` inside a pending prompt toggles always-approve mode, which drains the queued request with its first `AllowOnce` row. This is existing behaviour and must not be re-wired in this phase. |
| Unfocused state | When another pane has focus the panel recedes (`recede_area` at 0.66) and no row shows the cursor overlay — it must read as "no active selection", not as "row 1 is chosen". Hover paints `theme.hover_overlay()` and never the selection band. |
| Confirm | Selecting a row sends `Selected(option_id)` for that row and pops the request. The last confirmed allow/reject **kind** becomes sticky and steers the next prompt's cursor; the always-approve row is excluded from stickiness. |
| Cancel | `Esc` / `Ctrl-C` in the options focus sends `Cancelled` (a reject, never an allow). Cancelling must not fall through to a more permissive row. |
| Reject with feedback | The reject row is also an inline input: typing turns it into `❯ <feedback>` (first line, 50-column truncation) and submitting sends `PermissionFollowup`; the visible row is still the reject row. |
| Allow scope | `←` / `→` narrow or widen the persistent grant on the `allow-always-command` / `allow-always-mcp` row only, and the label re-renders as `Always allow: <words>` / `Always allow: all tools from <Server>` on the first keystroke. No scope toggle exists on the reject-always row for MCP. |
| Pattern editor | `e` opens the bash pattern editor; `Enter` saves, `Esc` cancels. The preview line states `✓ matches this command`, `✗ won't match this command`, `✗ matches everything, won't be saved`, and `⚠ very broad` with the exact strings above. |
| Expand | `Ctrl-F` toggles `args_expanded`, lifting the height cap to the full screen and the 5-row body cap. The indicator row disappears when expanded. |
| Focus loss | A prompt for a subagent renders a provenance line (`Subagent "<description>" (<type>):` or `Child session (untracked):`) in `gray` above the title. It is not a chip and carries no colour. |
| Queueing | Multiple requests queue in arrival order; the panel shows the front one and the height is recomputed for it. The mode chips never change because a prompt appeared. |

### Mode indicator

| Behaviour | Contract |
|-----------|----------|
| Placement | Chips live on the prompt's bottom-border info row, right-aligned with the model name, order: model name, mode chip, permission chip. `multiline` occupies the right end. |
| Coupling | Mode and permission are independent: `plan · always-approve` and `plan · auto-review` must both render two chips. Never collapse the pair into one. |
| Optimism | A Shift+Tab pick updates the chip immediately (`plan_mode_pending` / `session_mode_pending`) and the `Switched to mode:` banner names the pick; the confirmed `CurrentModeUpdate` reconciles without a second banner. |
| Plan exit | Leaving plan mode clears the plan chip and emits the `Plan {verdict} · plan mode off · active permission mode: {…}` row. An after-turn review that is still mounted defers the clear until `Default` confirms. |
| Before quit | The chip pair visible in the last frame before quitting is the reference frame for PERM-03's cast. |
| After `--resume` | The same pair must be visible again on the first drawable frame: the plan chip from the persisted session plan state (`plan_mode.json`), the permission chip from config / CLI flags (no flag on resume means the persisted `[ui] permission_mode`, not a reset to `ask`). The two must match the pre-quit frame. Provenance (which setting is session versus config) is documented in SESS-04's `notes.md`, not in this contract. |
| Always-approve under plan | Enabling always-approve while plan mode is armed toasts `⚠ Always-approve ON: plan mode still blocks file edits until you exit plan mode` — never the plain "all tool actions auto-run" copy, which would overpromise. |

### Headless denial

| Behaviour | Contract |
|-----------|----------|
| Trigger | A permission-gated tool in a `-p` run with no TTY to answer the prompt, and `--always-approve` not passed. |
| Fail-closed | The tool does not run. There is no auto-approve fallback, no retry with a wider policy, and no hidden mode change. |
| Order | `on_end` writes the result (stdout, format-dependent), then the hint line, then the `Error:` line. Both stderr lines are complete physical lines with no ANSI and no wrapping by the product. |
| Exit | Status 1, on both the plain and the JSON invocation. |
| JSON invocation | stdout carries `stopReason: "cancelled"` in the result object; the two stderr lines are the actionable hint. No new JSON key. |
| Yolo exemption | With `--always-approve` there is no hint and no error line; the turn ends `Ok(())`. |
| Idempotence | A second denial in the same run prints the pair again per turn; the strings never vary with the tool name, command, or path. |

## Rendered Surface Reference
