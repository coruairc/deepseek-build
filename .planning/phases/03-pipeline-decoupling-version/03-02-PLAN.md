<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| manifest -> compiled-in version | the version the binary reports is fixed at compile time and cannot be corrected at runtime |
| CI tag -> `GROK_VERSION` -> artifact | a wrong derivation stamps a wrong version into a shipped binary |
| source tree -> `Cargo.lock` | a stale lock silently re-resolved makes the build use versions nobody reviewed |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-05 | Repudiation | stale `Cargo.lock` | high | mitigate | The lock is regenerated by `cargo metadata` and asserted to differ by exactly the four package versions; `cargo metadata --locked` and `cargo check --workspace --locked` fail on disagreement; 03-01 adds `--locked` to the CI build so the same failure is loud remotely. |
| T-03-06 | Tampering | version string injected from an env var | medium | mitigate | `GROK_VERSION` is read at compile time only; the test proves the stamp wins with a sentinel that differs from the manifest, and the workflow derives the value from the tag and re-asserts it with a `deepseek-build <version> (` needle. |
| T-03-07 | Repudiation | "both paths print 0.1.0" claimed from one build | high | mitigate | Two invocations with the variable unset and set to a distinct sentinel; the test reads its expectation at runtime and asserts the full three-token shape. |
| T-03-SC | Tampering | npm/pip/cargo installs | high | mitigate | No dependency is added; the test uses only `std` and `env!`/`CARGO_BIN_EXE_`; no registry, action or tool is installed. |
</threat_model>
